# AI 协作记录（Prompt 链与 Bug 修复过程）

> 本文件按要求整理「至少 3 个核心功能迭代时与 AI 交互的完整 Prompt 链」，
> 包含：人类的意图（Prompt）→ AI 的方案与实现 → 决策依据 → 验证结果。
> 完整原始对话可通过 AI 编程助手（DeepSeek Harness）的会话日志导出功能获取。

---

## 迭代一：从一句话需求到选题定案

### 人类意图

> "我需要一天之内完成一个项目，按传智杯 AI 创新应用挑战赛的要求争取获得省级奖项。
> 选题方向有十个，你帮我选一个最容易拿分、且一天能做完的。"

### AI 的回应要点

AI 没有直接开始写代码，而是先做了三件事：

1. 读解评分表，指出 **「过程可复现 25% + 实用价值 25% = 50%」**，而「工程质量」只有 15%，因此策略应是「保交付、保过程记录」，而不是堆技术难度。
2. 指出奖项结构：一等 ≤10%、二等 ≤20%、三等 ≤30%、优秀 ≤30%，**完整交付即可拿到奖项**。
3. 给出三个候选方向的对比：多智能体看板（创新但易做成玩具）、轻量 RAG 知识库（技术含量高但演示平淡）、**AI 智能出题与批改引擎**（痛点真实、闭环完整、视觉效果好、且内部可自然嵌入多智能体流水线）。

### 决策

选择第三个方向。理由是它的「产品本身」与「评分里的方法创新」可以共用同一套机制——双智能体互检，既提升出题质量，又直接对应「意图控制」评分项。

### 验证

项目在当天完成全链路闭环，`node scripts/smoke.mjs` 一次性通过。

## 迭代二：核心架构 —— 双智能体互检 + 本地校验

### 人类意图

> "让 AI 出题，但它自己检查自己肯定说没问题。怎么保证出来的卷子是对的？"

### AI 的回应要点

提出三层结构：

1. **出题与审查彻底分离**：两次独立调用，不同系统提示词、不同上下文、不同温度（出题 0.85 / 审题 0.15）。审查者看不到生成者的推理过程，只能面对最终产物逐题核算。
2. **中间插入确定性结构校验**：题型、选项、答案是否在选项内、分值之和、解析是否存在——全部用代码判断，成本近乎为零。理由是「验证比生成便宜」。
3. **反馈环必须有闸门**：最多 2 轮修复，超限则降级交付并标记「待人工复核」，保证用户永远能拿到产物。

### 决策

全部采纳。同时在实现中补了一个细节：`totalPoints` 不采信模型输出，由服务端对题目分值求和后写回。

### 验证

首次冒烟测试：5 题 / 50 分，1 轮通过，10.2 秒，4209 tokens。

## 迭代三：真实 Bug —— 审题永不收敛（最有价值的一段）

### 现象

冒烟测试连续三轮审题未通过，全链路 23.4 秒、13,063 tokens，最终降级为「待人工复核」。

审题者提出的问题却是：

```
"各题分值之和为 8+10+10+10+12=50，总分正确；
 但 q1 为 easy 难度却给 8 分……单题分值分配不够合理（此项为次要问题）"
severity: "major"   ← 问题在这里
```

### 人类意图

> "为什么它一直在挑风格问题？是不是提示词的问题？"

### AI 的定位

根因不是模型笨，而是**契约没定义清楚**：提示词只写了「存在 blocker 或 major 就判不通过」，却从未定义什么算 major。模型于是把「值得改进」与「影响作答」混为一谈，而「找错误」这个角色设定又鼓励它多报问题。

### AI 提出的修复方案（三步）

1. **写死严重度判定标准**，并加入反向约束：
   - `blocker`：客观错误或无法作答/判分（答案错、单选多解、超纲）
   - `major`：明显影响质量但学生仍能合理作答
   - `minor`：风格、统一性、分值分配等建议性意见，**绝不允许写成 major**
   - 并明确告知：分值总和已由程序校验，不需要重复核算
2. **流水线层实现严重度收敛**：第 1 轮 blocker 与 major 都阻断；第 2 轮起仅 blocker 阻断。
3. **修复提示词补约束**：只修 blocker 与 major，不要为 minor 大改题目。

### 决策与取舍

有人可能会想「是不是应该让审题更聪明」。这里放弃了这条路——**让 AI 更聪明地挑错是一个无底洞**，而「让 AI 只对客观错误负责」是一个有界问题。这是本项目的核心判断：遇到模型不确定性，优先改系统结构，而不是反复调提示词。

### 验证（同一用例对比）

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 审题轮次 | 3 轮（仍未通过） | 1 轮（通过） |
| 全链路耗时 | 23.4 s | 10.2 s |
| token 消耗 | 13,063 | 5,426 |
| 交付状态 | 待人工复核 | 正常交付 |

## 迭代四：工程健壮性 —— 演示前清库导致写盘失败

### 现象

为了录制演示数据，在服务运行中删除了 `server/data` 目录，随后生成接口报错：

```
[sse] handler error: Error: ENOENT: no such file or directory,
open '.../server/data/papers.json.tmp'
```

### 原因

`store.js` 用一个 `ready` 布尔值缓存「目录已创建」这一事实。目录被外部删除后，缓存仍然为真，写盘直接失败。

### 修复

写入前无条件确保目录存在（`mkdir -p` 是幂等的，成本可忽略），不再依赖缓存状态。

### 附带改进

`dev.mjs` 中的服务端进程改为 `node --watch` 启动，减少开发期手动重启。

## 迭代五：UI 质量 —— 三处真实缺陷

这一轮体现了「AI 生成 + 人验收」的工作方式：AI 写完界面后，人类用真实截图验收，指出问题。

### 问题一：报告页公式没有渲染

逐题明细里显示的是 `$\lim_{x \to 0} \frac{\sin 3x}{x}$` 原始文本。

**修复**：把题干与批改反馈一并交给自研的 `RichText` 组件渲染，KaTeX 正常出图。

### 问题二：知识点雷达图标签被裁切

长中文知识点名（如「微分中值定理」）超出 SVG 视口，显示成「值定理 33%」。

**修复**：移除图内文字标签，改为雷达图下方图例列表；同时知识点少于 3 个时自动退化为条形图，避免多边形无法构成。

### 问题三：新建试卷页右侧空白

未开始生成时右侧只有一个「等待启动」。

**修复**：补充四步流水线说明，用户在等待前就理解将要发生什么。

### 验证

三处修复后重新截图核对，均正常。

## 迭代六：多学科回归暴露的「分值漏网」

### 现象

更换三个学科做回归测试时，概率论的试卷要求总分 60，实际只有 52，**但审题依然判定通过，错误直接交付**。

### 定位

这是一个典型的「双方都以为对方会管」：

- 本地结构校验确实算出了「总分不符」，但流水线只把它当作一条 warn，没有阻断能力；
- 审题提示词里又写着「总分已由程序校验，你不需要再核算」——审题者于是跳过了这项检查。

结果两个环节都没兜住。

### 修复（双管齐下）

1. **一票否决**：交付条件改为 `审题通过 && 本地硬校验通过`；流水线末尾再加一道闸门，结构不合法绝不标记为通过，并标注「待人工复核」。
2. **确定性归位**：分值加总本质是算术问题，不需要花一轮模型修复。归一化阶段直接从分值最大的题开始吸收差值，把总和精确补齐，并保证每题不低于 1 分。

### 取舍

第二条修复是本项目最能说明「验证比生成便宜」的例子：同样一个错误，交给模型修复需要一轮调用（约 8 秒、4000 tokens），交给算术只需要几行代码和零成本。

### 验证

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 分值 | 52 / 60（错误交付） | 60 / 60（自动归位） |
| 审题轮次 | 2 轮 | 1 轮 |
| 耗时 | 18.7 s | 9.6 s |
| token | 13,143 | 5,067 |

三学科回归最终 **3/3 全部通过**。

## 迭代七：审题者的自相矛盾（契约重构）

### 现象

修好「分值漏网」后，回归测试仍然有一个学科反复不通过。查看审题输出：

```
"severity": "blocker",
"detail": "……经复核本题无问题，三个反例均成立，不构成 blocker。"
```

模型在自己的 detail 里论证了「这道题没问题」，却仍然标成 blocker、判不通过。

### 定位

根因是输出契约留了模糊空间：`{passed, issues[{detail}]}` 里的 detail 是自由文本，模型可以在里面写思考过程，结果写出了「其实没问题」的结论，却忘了撤回上面的 severity。

### 修复

把契约改成**逐题二元裁定**：

```json
{"verdicts":[{"questionId":"q1","ok":true,"category":"none","severity":"none","evidence":""}],"summary":"..."}
```

- 每道题必须出现且只出现一次；
- ok=false 时必须写出**可被第三方核对的错误证据**（如正确选项序列），写不出证据就必须 ok=true；
- 禁止在 evidence 里写推理与改口；
- 程序不再信任布尔结论，改为根据 ok 与 severity 重新判定；输出结构缺失则判定为审题异常并重试。

### 验证

| 指标 | 旧契约 | 新契约 |
|---|---|---|
| 数据结构用例 | 3 轮仍未通过 | **1 轮通过** |
| token | 15,476 | **4,482** |
| 三学科回归耗时 | 48.5 s | **37.8 s** |
| 三学科回归通过率 | 2 / 3 | **3 / 3** |

### 方法论

模型不稳定时，收紧**输出契约的结构约束**比反复调措辞更有效：
把「请你想清楚」变成「你必须逐项给出可核对的判断」。

## 协作方式总结

| 环节 | 谁负责 |
|---|---|
| 意图定义、选题取舍、评分策略 | 人类 |
| 架构设计、代码实现、文档生成 | AI |
| 验收标准制定、缺陷判定、真机验证 | 人类 |
| 性能测量、回归测试、复现验证 | AI（结果由人类抽查） |

**结论**：AI 把「写代码」的成本压到了接近于零，但「定义问题、设计约束、判断结果好不好」的成本并没有降低，反而成了决定成败的部分。
