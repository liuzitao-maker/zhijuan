## 先建立一个正确的心智模型

我不是“问答机器人”，是**能动手干活的代理**：能读你的文件、跑命令、装依赖、搜网页、改代码、起后台任务、定时提醒、开子代理。所以学习的重点不是“怎么问得漂亮”，而是：

> **怎么给我一个目标 + 素材 + 验收标准，然后验收我的产出。**

## 给需求的三件套

| 要素 | 反例 | 正例 |
|---|---|---|
| 目标 | “帮我弄一下这个项目” | “把这个项目的构建时间从 40s 降到 15s 以内” |
| 约束 | （无） | “别动 CI 配置；不要新增依赖；保持 API 兼容” |
| 验收 | “你看看行不行” | “`pnpm test` 全绿，并且给出改动前后耗时对比” |

三个都给了，我的产出质量会差一个数量级。缺了验收标准，我就会自己编一个——而那往往是错的。

## 分四层练，每层一个具体任务

**第 1 层 · 单文件操作**（今天就能做）
让我在工作区建一个文件、改一个文件、解释一个文件。目的是熟悉“我看得见你的过程、你能看我的 diff”这个协作节奏。
→ 练习：*“在工作区建一个 `hello.md`，写今天学到的三件事，然后读给我听。”*

**第 2 层 · 带外部信息与多步骤**
搜索 + 抓网页 + 整理成结构化文档。目的是学会给我“信息源要求”而不是让我猜。
→ 练习：*“搜三个关于 X 的方案，抓原文，做成对比表格存成 md，每行标注来源链接。”*

**第 3 层 · 需要验证的工程任务**
写脚本 / 改代码 / 跑测试。关键动作是**要求我给出可验证证据**（命令输出、测试结果、diff），而不是让我口头保证。
→ 练习：*“写个 Python 脚本把这目录下的 csv 合并去重，自己跑一遍，把输出贴出来。”*

**第 4 层 · 让我“持续跑”的能力**
这是大多数人不会用、但价值最高的部分：
- **目标（goal）**：把长任务交给我，我会跨轮次自动续跑直到完成；
- **定时任务（schedule）**：每天/每周定点提醒或巡检；
- **子代理 / Agent Teams**：可以并行拆活，比如“一个查资料、一个写实现、一个做评审”；
- **技能（skill）与插件**：把可复用的做法固化成能力，而不是每次重新说。

## 最该学的其实是“验收”

我最大的风险是**流畅地自信犯错**。所以请养成三个习惯：
1. 关键改动前说一句“**先说计划，等我确认再动手**”；
2. 涉及删改时说“**先备份 / 用 git，改完给我看 diff**”；
3. 结论类任务要求“**给出依据和出处**”，没有来源的都当草稿。

另外：*“不确定就问我，不要猜”* 这句话请经常用，它比任何提示词技巧都有效。

## 一个反直觉的建议

不要花时间研究“提示词大全”。我的能力边界**只有撞到才知道**：你会慢慢发现哪些事我十秒搞定、哪些事我做得很糟（比如凭记忆写精确数字、长时间保持细节一致性）。这份“边界地图”才是你真正的学习成果，只能靠真实任务积累。

## 作为新手，AI 到底该怎么学

核心原则只有一条：**不要"学 AI"，要用 AI 去完成事。** 学习是副产品。

具体来说，一个可执行的循环（这也是我认为唯一有效的循环）：

1. **从你真实的痛点出发**，不要从教程出发。你工作/生活里哪件重复的、烦人的、要查很久的事？就它。
2. **端到端做完一次**——让 agent 从头到尾交付，你只负责给目标、给约束、验收。
3. **记录失败点**——它在哪里胡说、哪里漏了约束、哪里需要你补信息。这张"边界地图"才是你的资产。

时间上，我建议：**每天 20–30 分钟动手，每周一次 2 小时完整小项目**，同时把信息流砍到每周一次。这个强度三个月，你会明显超过大部分天天刷新闻的人。

## 承重的那 5%（这是我上一条该给你而没给的）

这些内容认真学+动手验证，大概两三周，不是读个学位：

1. **模型是条件概率续写器** → 由此推出它为什么没有"不知道"的直觉，为什么会一本正经胡说。
2. **训练截止与幻觉机制** → 由此推出什么时候必须喂外部信息、什么时候不能信它。
3. **上下文窗口与注意力衰减** → 由此推出长对话为什么会丢细节、为什么"中间的信息"最容易丢。
4. **token 与分词** → 由此推出它数数、精确切字符串、处理中文/代码细节为什么会错。

## 分歧点：原理 ≠ 边界，而边界只能靠实证校准

这是我真正想跟你讨论的地方。原理能告诉你**"这类任务理论上它可能出错"**，但它**不能告诉你"这一版模型在这个具体任务上到底错多少"**。因为边界是训练数据分布 + 对齐方式 + 当前版本的函数，而这些每个版本都在变。

所以完整的公式是：

> **真正的高手 = 原理（能预测）+ 实证（能校准）+ 应用（能兑现）**

原理让你**知道该往哪撞、以及为什么撞了**；实证让你**知道现在撞在哪**；应用让你**把撞出来的东西变成产出**。三者互相喂养，缺一不可。你强调的是前两者，我上一条强调的是第三者——其实我们各自漏了对方的半边。

而且有个更狠的点：**你问我"你的边界在哪"，我不是可靠信源。** 模型对自己的内省是不可靠的——我会编造一个听起来很合理的失效模式。所以"了解能力边界"这件事，某种程度上**只能从外部做**：看论文、看评测榜、自己跑实验。这恰恰又支持了你的论点——**不理解机制的人，连该做哪个实验都不知道**。

## 那"了解 AI 发展"到底要不要

- 新闻 = 噪音，半衰期一天，作用是生产焦虑；
- 方向 = 信号，比如"推理成本在降""上下文在变长""agent 从演示走向可靠性"——这类结构性变化，**半年看一次**就够，而且它决定了你该把能力押在哪。

## 所以一个更准确的"新手路线"

不是"先学原理再上手"，也不是"先上手再补原理"，而是**双螺旋**：

1. **上手跑一个真实闭环**（我上一条说的那件事）；
2. **每次它翻车，倒推是哪一层的问题**——这是学原理最高效的方式，比读教材快十倍，而且天然符合你说的"在工作生活中应用"；
3. **攒出一张自己的"边界地图"**，但每条都标注**是原理推出来的、还是实测出来的**；
4. **每三个月回头校准一次**：哪些结论已经过期了（模型更新了），哪些还成立（这说明你摸到了原理层）。

## 一、把五个词放回各自的层

- **大模型** = 大脑，只会想和说
- **上下文** = 工作记忆，能同时“想”多少

## 二、你说的流水线有名字，难点不在流程图

你描述的：A 做 → B 检查 A → C 检查 B → B 发现 A 错就退回让 A 改。这是一个**带回边的有向图**（不是顺序流程图），行业里叫“带质量门的工作流”，学术上叫 generator–verifier、self-refine、reflexion，检查者叫 critic 或 LLM-as-judge。

**2. 验证必须比生成便宜。** 流水线能赚，靠的是“生成很难、检查很容易”（写代码难，跑测试容易）。如果检查也需要同等智力，那就没有收益，只是多花了一次算力。

**3. 检查者会放水。** 这是你观察得最准的一点。AI 检查 AI，如果是“同一个人格”，它会偏向自己的输出，倾向于说“看起来不错”。所以独立检查者必须：独立上下文 + 敌对性提示（“找出它错在哪，找不到就继续找”）+ **硬标准**（测试、编译、实际运行），而不是“你觉得对不对”。

另外要知道风险：三级反馈环会让错误**复利**，还可能死循环。所以要定预算和终止条件——“最多迭代 3 轮，还不过就交给人”。
